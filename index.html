The three essentials

1Governed data access

The tool reads a reporting copy through a read-only login, never production. People who own the data decide what it can see. ACCESS.md

2Verify before it ships

Source, method, and a challenge for every number, then a human reviewer signs off. CHECKLIST.md

3Knowledge written down

The rules that live in one person's head, captured once, so your team and your tools follow the same ones. report_rules.md

Try it in 15 minutes

You need Python 3.9 or later. Nothing else to install.

python data/make_sample_data.py      # rebuild the fake data (optional, it's included)
python report/build_report.py        # build the report
python check/verify.py               # 14 checks; exit code 0 = OK to send
python check/verify.py --challenge   # prove the checks can fail
python report/build_report.py --compare-by calendar --out report/out_mistake
python check/verify.py --summary report/out_mistake/summary.json   # watch it catch the mistake

Then make it yours

  1. Pick the report. One someone builds by hand every week. Registration pacing is a good first one.
  2. Write the rules down. Sit with the person who builds it, record them talking through it, and fill in rules/report_rules.md. Read it back to them.
  3. Get read-only access. Use the request in ACCESS.md. Build against fake or de-identified data first.
  4. Have AI draft the script. Use prompts/01_build_report.md with an AI tool your school approves.
  5. Verify, then hand it back. Run the checks, then show the first real report to the person who used to build it. They sign off.
